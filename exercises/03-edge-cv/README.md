# تمرین ۳: رزومهٔ شما روی لبهٔ اینترنت

> جلسهٔ ۵ · مهلت: پنجشنبه ۲۱ آبان ۱۴۰۵، ساعت ۲۳:۵۹

## در یک نگاه

| | |
| --- | --- |
| **چه می‌سازید** | یک صفحهٔ رزومهٔ ساده روی Cloudflare Workers، با نشانی `https://cv.ie1405-<شمارهٔ دانشجویی>.workers.dev` |
| **چه یاد می‌گیرید** | متدهای HTTP و headerهای cache روی یک سایت واقعی که روی سرورهای لبهٔ یک CDN اجرا می‌شود |
| **چگونه نمره می‌گیرید** | تمام‌خودکار: آزمون‌ها روی سایت زندهٔ شما اجرا می‌شوند و سه سؤال چندگزینه‌ای با کلید مقایسه می‌شود |
| **هزینه** | هیچ؛ پلن رایگان Cloudflare کافی است و کارت بانکی لازم نیست |

رزومه می‌تواند چند خط باشد: نام، رشته و چند مهارت. اگر خواستید زیبایش کنید، برای خودتان است و نمره‌ای ندارد. نام مستعار یا فقط نام کوچک هم قبول است؛ ایمیل و تلفن لازم نیست.

## پیش از شروع، به این فکر کنید

لازم نیست جوابتان را جایی بنویسید یا تحویل بدهید.

صفحهٔ رزومه را با `Cache-Control: public, max-age=300` می‌فرستید. دوستتان صفحه را باز می‌کند، و یک دقیقه بعد شما متن رزومه را عوض می‌کنید و دوباره منتشر می‌کنید. اگر دوستتان صفحه را دوباره باز کند، چه می‌بیند؟ و فایل css که در نامش هش دارد چطور؟

## آماده‌سازی

1. داخل `ie-course-scu` دستور `git pull` را بزنید، در مخزن خودتان پوشهٔ `ex03/` را بسازید، و محتوای `starter/` و پوشهٔ `check/` را در آن کپی کنید.
2. در [dash.cloudflare.com/sign-up](https://dash.cloudflare.com/sign-up) یک حساب رایگان بسازید.
3. در بخش **Workers & Pages**، کنار **Your subdomain** دکمهٔ **Change** را بزنید و `ie1405-` و بعد شمارهٔ دانشجویی‌تان را بنویسید، مثلاً `ie1405-401234567`.
4. یک Worker تازه با نام `cv` بسازید و **Deploy** را بزنید. نشانی `https://cv.ie1405-401234567.workers.dev` حالا باز می‌شود.
5. دکمهٔ **Edit code** را بزنید، محتوای `worker.js` را جای کد نمونه بگذارید و دوباره **Deploy** را بزنید.

از اینجا به بعد، `worker.js` را در مخزن خودتان ویرایش کنید و هر بار در ویرایشگر Cloudflare منتشر کنید. اگر با خط فرمان راحت‌ترید، در `ex03/` دستور `npm install wrangler` و بعد `npx wrangler login` و `npx wrangler deploy` را بزنید؛ برای اجرای محلی هم `npx wrangler dev`.

فایل `worker.js` آغازین همین حالا یک صفحه نشان می‌دهد، ولی به هر درخواستی، با هر متد و هر مسیر، همان صفحه را می‌دهد. کار شما این است که آن را به جدول زیر برسانید. کتابخانه و چارچوب لازم نیست؛ `fetch` و `Response` و `crypto.subtle` کافی است.

## چه چیزی بسازید

| درخواست | پاسخ |
| --- | --- |
| `GET /` | `200` با رزومه به‌صورت HTML، که نام و شمارهٔ دانشجویی شما را دارد؛ `Cache-Control: public, max-age=300` و یک `ETag` |
| `GET /` با `If-None-Match` برابر همان `ETag` | `304` بدون بدنه |
| `GET /cv.json` | `200` با همان رزومه به‌صورت JSON، دست‌کم با `name` و `studentId`؛ `Cache-Control: public, max-age=300` |
| `GET /style.<هش>.css` | فایل css صفحه، که صفحه با `<link>` به آن پیوند داده است؛ `Cache-Control: public, max-age=31536000, immutable` |
| `POST /contact` | فرم «پیام بگذارید» در صفحه به اینجا ارسال می‌شود؛ پاسخ `303` با `Location: /thanks` |
| `GET /thanks` | `200` با یک پیام تشکر؛ `Cache-Control: no-store` |
| `HEAD` روی هر مسیری که `GET` دارد | همان headerها، بدون بدنه |
| `OPTIONS` روی هر مسیر موجود | `204` با فیلد `Allow` |
| متد دیگر روی مسیر موجود، مثل `DELETE /` یا `GET /contact` | `405` با فیلد `Allow` |
| مسیر ناموجود | `404` |

سه نکته:

- پیام فرم لازم نیست جایی ذخیره شود.
- مقدار `ETag` را از هش بدنه بسازید (`crypto.subtle.digest`) تا با عوض شدن متن رزومه عوض شود.
- سرویس Cloudflare گاهی هنگام فشرده‌سازی پاسخ، `ETag` شما را با پیشوند `W/` به مرورگر می‌دهد. پس در مقایسهٔ `If-None-Match` این پیشوند را نادیده بگیرید؛ [بخش ۱۳.۱.۲ از RFC 9110](https://www.rfc-editor.org/rfc/rfc9110#section-13.1.2) هم همین مقایسهٔ ضعیف را می‌خواهد.

## سؤال‌های answers.json

هر پاسخ آرایه‌ای از شماره‌هاست، مثلاً `"after_post": [1, 4]`. ممکن است بیش از یک گزینه درست باشد.

**سؤال اول (`hit_ratio`):** در مثال کتاب (بخش ۲.۲.۵: لینک دسترسی ۱٫۵۴ مگابیت، ۱۵ درخواست در ثانیه، هر object صد کیلوبیت، تأخیر اینترنت دو ثانیه)، اگر نرخ برخورد cache دانشکده به‌جای ۰٫۴، ۰٫۶ باشد، کدام گزاره‌ها درست‌اند؟

1. بهره‌وری لینک دسترسی حدود ۰٫۳۹ می‌شود.
2. بهره‌وری لینک دسترسی حدود ۰٫۶ می‌شود.
3. تأخیر میانگین حدود ۰٫۸ ثانیه می‌شود.
4. تأخیر میانگین از حالت لینک ۱۵۴ مگابیتی بدون cache بیشتر می‌شود.

**سؤال دوم (`who_sees_cookie`):** کسی با HTTPS به رزومهٔ شما وصل است و کوکی دارد. در کدام حالت‌ها، واسطهٔ نام‌برده مقدار کوکی را به‌صورت متن ساده می‌بیند؟

1. شبکهٔ CDN جلوی سایت؛ یعنی همین Worker شما.
2. یک forward proxy که اتصال را با `CONNECT` تونل می‌کند.
3. واسطهٔ سازمانی (proxy) که گواهی ریشهٔ خودش را روی رایانهٔ کاربر نصب کرده است.
4. نقطهٔ دسترسی Wi-Fi دانشکده.

**سؤال سوم (`after_post`):** کسی فرم پیام را در رزومهٔ شما می‌فرستد و Worker پاسخ `303` به `/thanks` می‌دهد. کدام گزاره‌ها درست‌اند؟

1. مرورگر برای `/thanks` دوباره `POST` با همان بدنه می‌فرستد.
2. مرورگر برای `/thanks` یک `GET` می‌فرستد.
3. اگر کاربر در صفحهٔ `/thanks` دکمهٔ بارگذاری دوباره را بزند، پیام دوباره فرستاده نمی‌شود.
4. اگر به‌جای `303` پاسخ `307` بدهید، رفتار مرورگر همین است.

## اگر خواستید بیشتر بدانید

این بخش‌ها نمره ندارند.

- **این پاسخ از کجا آمد؟** در صفحه نشان دهید درخواست از کدام مرکز دادهٔ Cloudflare پاسخ گرفت (`request.cf.colo`) و با کدام نسخهٔ HTTP و TLS رسید (`request.cf.httpProtocol` و `request.cf.tlsVersion`). آن را با Wi-Fi دانشگاه و اینترنت همراه مقایسه کنید.
- **ذخیرهٔ پیام‌ها.** پیام‌های فرم را با [Workers KV](https://developers.cloudflare.com/kv/) ذخیره کنید و فقط برای خودتان نشان دهید. صفحهٔ پیام‌ها چه headerی برای cache لازم دارد؟
- **دامنهٔ خودتان.** اگر دامنه دارید، Worker را روی آن بیاورید و یک پاسخ را با [Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/) در لبه نگه دارید. چرا این کار روی نشانی `workers.dev` اثری ندارد؟

## پل به جلسهٔ ۶

اگر بخواهید وقتی کسی برایتان پیام گذاشت، صفحهٔ باز رزومه همان لحظه خبردار شود چه؟ صفحه می‌تواند هر چند ثانیه یک بار بپرسد «پیام تازه‌ای هست؟»، ولی بیشتر جواب‌ها «نه» است. جلسهٔ ۶، «فراتر از request/response»، دربارهٔ راه‌هایی است که سرور بی‌آنکه کلاینت بپرسد، به او خبر بدهد.
